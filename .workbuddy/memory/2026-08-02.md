## 好友专用车位解锁 bug 修复（app.js，本地未上传）
- 现象：第3/4位好友车位（需10/20好友）满足好友数仍不解锁；第1/2位（0/3好友）正常。
- 根因：原 `checkFspotUnlock()` 只在 ① 启动时（跑在登录前的本地档，好友数0）② `addFriend`/`acceptFriend` 内调用。`proceedAfterLogin` 登录成功后会再次 `load()` 载入云端真实存档（含20好友），但**这次载入后没有重新判定**，导致第3/4位停在旧存档的锁定态，永远不解锁。
- 修复：
  1. 把 `const FSPOT_FRIEND_THRESHOLDS = [0,3,10,20]` 上移到 `load()` 之前定义（避开 const TDZ，否则 load 内调用会报未初始化）。
  2. 在 `load()` 末尾（所有迁移/归一化之后、`return true` 前）调用 `checkFspotUnlock()`，使每次载入存档都按当前好友数重判（含登录后云端重载）。
  3. 删除启动时的重复调用（已并入 load）。
- 验证：Node 仿真——20 好友 → 4 车位全解锁 PASS；`node --check` 语法 OK。

## 激励视频广告反复弹出的 bug 修复（chexing-sdk.js，本地未上传）
- 现象：没看完广告退出会反复自动打开广告；有时看完也领不到奖励、广告还反复打开。
- 根因：三个调用方（充值 watchAd / 兑换 doExchange / 转盘/首充 fc-watch-ad，gachaSpin）都是单次点击触发、不会自循环。问题在共享桥 `showRewardAd` 的 `isTapMiniGame` 分支：`onLoad(()=>ad.show())` 在 TapTap 激励视频**实例被复用**、且关闭后 SDK 会**再次触发 onLoad** 时，会反复 `show()` 拉起广告（旧代码无 `shown` 防重展示锁，且每次调用都重新 `createRewardedVideoAd` + 叠加 onLoad/onClose 监听）。
- 修复（chexing-sdk.js + h5-build/chexing-sdk.js，两处同步）：
  1. 模块级 `_rewardAdBusy` 防连点锁：播放中再点直接返回 `{success:false, msg:'ad_busy'}`，避免叠加多则广告。
  2. 每则广告 `let shown=false`：`onLoad` 内若已展示过则 `return`，切断"关闭后 SDK 重发 onLoad → 再次 show()"的无限循环。
  3. `onClose`/`onError` 结算后 `ad.offLoad/offClose/offError/destroy()`（try/catch 容错）解绑并销毁实例，避免 TapTap 复用该实例时残留监听再次拉起。
- 验证：Node 真实加载 SDK + 模拟"关闭后 SDK 反复 onLoad"的恶意图桥，3 项仿真全 PASS——show() 调用次数恒为 1、看完正确发奖、中途关闭只 1 次且不发奖、连点被 ad_busy 拦截。`node --check` 根/h5 两文件语法 OK。
- 状态：**已打包上传**：用户下"打包更新"指令，走标准流程 → 版本号 tt18→tt19、sync h5-build（md5 全一致）、commit `1ec570e`、SSH push `72bbe82..1ec570e` 触发 GitHub Actions 构建 `qcwhxjq.apk`；安全上传 895103（get_current_app_info 再次抓到缓存被静默篡改为 897266 扫雷，select_app 切回 895103，prepare 核对无误后 upload），get_app_status 真实状态 **已上线(1)/审核状态已上线(4)**，开发者立即可测。qc_stage 已清理。

## 广告反复弹出 bug 二次加固（tt20，本地未上传）

- 修复（chexing-sdk.js）：`onLoad/onError/onClose` 改为**具名 handler**，解绑时 `ad.offLoad(onLoadH)` 按引用移除；`cleanup()` 统一在 `finish` 时调用 `offLoad/offClose/offError + destroy()`。`shown` 防重展示锁 + `_rewardAdBusy` 防连点锁保留。
